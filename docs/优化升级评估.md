这个项目的**工程质量其实不低**，不该被"好久没重大更新"这句话误导：

- 99 个测试文件 / 242 个源文件，覆盖比例健康，`src/themes/builtin.test.ts` 甚至做了"列表项内链接色 == 段落内链接色"的防回归断言；
- `useStore()` 全部带选择器订阅，**0 处**全量订阅；`console.log` 残留 **0 处**；
- 大依赖已经拆得很讲究：juice / mermaid / MathJax / pdfjs 全部按需加载，`vite.config.ts` 有精细的 `manualChunks`；
- CSP 收得很紧，Rust 侧有完整的单元测试。

**真正缺的不是"修 bug"，而是产品能力边界**：用户能换 14 套主题、能换 250+ 代码配色、能调毛玻璃和状态栏透明度，**却调不了正文字号**。这是当前最容易变现成"重大更新"的缺口——也正是你说的那个点。

## 1. 焦点问题：主题字号为什么调不了

### 1.1 现状：字号被硬编码在主题 CSS 里

14 个内置主题共有 **约 300 处 `font-size` 声明**，全部是绝对 `px`：

| 主题 | `font-size` 声明数 |
| --- | --- |
| `see-yue`（望月） | 30 |
| `mdnice-10`（青岚） | 29 |
| `mdnice-1`（暮橙） | 27 |
| `ink-haze`（墨岚） | 21 |
| `morandi-garden`（雾屿） | 10 |

以默认主题为例（`src/themes/builtin/ink-haze.css`）：

```css
#article        { font-size: 16px; }   /* :43  */
#article h1 .content { font-size: 31px; }   /* :83  */
#article h2 .content { font-size: 22px; }   /* :109 */
#article h3 .content { font-size: 19px; }   /* :147 */
#article h4 .content { font-size: 17px; }   /* :160 */
#article h5 .content { font-size: 16px; }   /* :162 */
#article h6 .content { font-size: 15px; }   /* :164 */
```

**关键点**：标题字号是**绝对 px，不是相对根字号的 em**。所以哪怕在 `#article` 上改 `font-size`，标题也纹丝不动——层级比例是主题作者写死的。

### 1.2 用户侧完全没有入口

- `SettingsDialog.tsx:294-299` 的五个分区是：微信配置 / 文件同步 / 网络辅助 / **外观** / 关于。这里的"外观"管的是**应用界面**（亮暗、配色、背景图、毛玻璃），**不含文章排版**；
- `ThemePickerDialog.tsx:28` 只有两个 tab：`markdown` / `code`；
- 唯一的办法是让用户自己写一个 CSS 主题文件——等于**要求用户成为主题作者**。

### 1.3 更隐蔽的坑：雾屿主题用了 `rem`

`src/themes/builtin/morandi-garden.css` 的**全部标题字号用 `rem`**：

```css
#article h1 { font-size: 2.2rem; ... }
#article h2 { font-size: 1.8rem; ... }
#article h3 { font-size: 1.5rem; ... }
#article h4 { font-size: 1.3rem; ... }
#article h5 { font-size: 1.1rem; ... }
#article h6 { font-size: 1rem;   ... }
```

`rem` 相对的是**应用根元素 `<html>` 的字号**（`globals.css:292` 未给 `html` 设字号，即浏览器默认 16px），**不是文章容器**。

探针实测（jsdom + 真实渲染管线）：

| 操作 | 正文 `p` | 标题 `h1` |
| --- | --- | --- |
| 原样 | 16px | 2.2rem（= 35.2px） |
| 把 `#article` 字号改成 20px | **20px** | **2.2rem —— 纹丝不动** |
| 把 `html` 字号改成 20px | 16px 不动 | **跟着变 44px** |

结论：**雾屿的标题既不受文章控制，又被应用 UI 字号绑架**。而且它的 `margin` / `padding` 也大量用 rem（`margin: 1.8rem 0 1rem`），间距同样被绑架——如果以后给应用加"界面字号"设置，雾屿的排版会整体错乱。

### 1.4 已验证的解法（我跑了探针，结论可信）

核心思路：**主题载入时做一次 CSS 文本级归一化 + 按倍率缩放**。

两步处理：

1. **`rem` → `px` 折算**（基准 16px）：把雾屿这类主题的标题从"被绑架"改回"可控制"；
2. **按倍率重写 `font-size`**：把所有 `font-size: Npx` 改成 `N × scale` px。

**为什么用"重写 CSS 文本"而不是 CSS 变量？**

- 微信会剥离根元素上的 `--x` 定义（你项目文档 `docs/用户主题制作指南.md` §8.9 已实测记录，墨岚 v2 就是栽在这），`var()` 方案在导出链路上有真实风险；
- 重写后落地的是**字面 px**，juice 内联、微信渲染、导出 HTML/PDF/长图全部天然一致，零额外分支；
- **相对单位（`em` / `%` / `rem`）原样保留**——它们随父级自动缩放，正好是想要的行为。

**实测结果**（scale = 1 / 1.25 / 0.9，墨岚）：

| 选择器 | ×1 | ×1.25 | ×0.9 |
| --- | --- | --- | --- |
| `h1 .content` | 31px | 38.8px | 27.9px |
| `h2 .content` | 22px | 27.5px | 19.8px |
| `h3 .content` | 19px | 23.8px | 17.1px |
| `p` / `blockquote` | 16px | 20px | 14.4px |
| `table` | 15px | 18.8px | 13.5px |
| `p code` | 0.88em | **0.88em** ✅ | **0.88em** ✅ |

- 相对单位被正确保护（行内代码保持 `0.88em`，实际渲染随父级缩放）；
- `@media` 块内的字号也被正确处理（`24px → 30px`）✅；
- 跨主题一致性已验证：暮橙、素简、墨岚·星空、墨岚均正常；
- 雾屿折算 rem 后：`h1` 从"不可控的 2.2rem"变成 **35.2px**，此后可正常缩放 ✅。

### 1.5 落地位置（改动面很小）

| 文件 | 改动 |
| --- | --- |
| `src/themes/fontScale.ts`（新增） | `normalizeRemToPx(css)` + `scaleFontSizes(css, scale)` |
| `src/themes/index.ts` | `ThemeOption` 增加 `rawCss`（已作用域、未缩放）；`css` 改为按 `(themeId, scale)` 记忆化派生 |
| `src/store/index.ts` | 新增 `articleFontScale: number`（persist + `merge` 里 sanitize） |
| `src/components/Preview/Preview.tsx:187-190` | 主题注入 effect 增加 `fontScale` 依赖 |
| `src/markdown/codeThemes.ts:42` | 代码块基准字号 `14px` 需同步缩放，否则代码块会脱节 |
| `src/components/Theme/ThemeThumbnail.tsx` | 缩略图固定用 `scale = 1`，不受影响 |

**性能无压力**：缩放是对几 KB 的 CSS 文本跑一次正则，只在主题或倍率变化时执行；主题 CSS 本来就已经在载入时 `scopeCssTo` 过一次并缓存（这一点做得对）。

### 1.6 最终实现（与 1.4/1.5 的差异：从"单一倍率"变成"按角色"）

1.4/1.5 是最初的设计（`fontScale.ts` + 一个 `scale`）。实际落地时改成了
`src/themes/typography.ts` + 状态 `{global, roles}`，因为"全局一个倍率"满足不了
"点标题只放大标题"这个需求。**以下规则改代码前必须遵守，违反任意一条都会出可见 bug：**

- **两条缩放规则**：
  - `px` 值乘 `global × roleScale`；
  - `em` / `%` **只乘 roleScale**（它已随父级缩放，再乘 global 会重复放大）；
  - 例外：**根元素 `#article` 的 em 要吃 global**（它之上没有已缩放的内容）。
- `normalizeRemToPx`（基准 16px）**无条件执行**，与用户有没有调倍率无关。
- 主题没声明字号的角色 → 补 `#article <target> { font-size: <scale>em }`；
  已声明过的角色**不补**（否则二次放大），靠 `declared` Set 跟踪。
- 一条规则里多个选择器角色不同时，**必须按角色拆开**分别缩放。
- 角色表的 `scope`（DOM 命中 + 高亮）与 `target`（CSS 覆盖）**必须分开**：
  li 是 `scope:"li"` / `target:"li section"`，h2 是 `scope:"h2"` / `target:"h2 .content"`。
  给 li 的 target 写成 `li`，会在 li 与 li section 上叠乘 em 而放大两次。
- 调用链：`buildMarkdownCss(css, codeThemeId, typography)` 内部最后统一 `scaleThemeCss` 一遍
  （代码块基准 14px 由此跟着缩放）；`buildCodeThemeCss` 内部那次传 DEFAULT，**避免二次缩放**。
- 导出安全：`.vs-role-outline`（预览描边）由 `stripPreviewArtifacts` 摘掉；描边样式写在
  `globals.css` 而非注入的 markdown style，所以 juice 不会把它内联进成品。
- 新增角色：加进 `FONT_ROLES`（`scope`/`target` 都要能被 `classifySelector` 正确归类），
  `typography.test.ts` 里"角色表里的 scope / target 选择器都能被正确分类"会自动校验。

### 1.7 需要你拍板的三件事

1. **入口放哪**：主题弹层底部（离"换主题"最近，心智一致）／设置里新增"排版"分区／预览工具栏 A- A+
2. **作用范围**：全局一个值／每篇文档独立（跟 `documentThemeIds` 一样按文档存）
3. **缩放对象**：只缩正文／正文 + 标题／正文 + 标题 + 间距（即"字号 + 密度"两个滑杆）

### 2.1 为什么放弃了「单次遍历」重构（实测，已撤回原判断）

我原本的判断是"7 个 effect 各自扫全树 = 每次渲染扫 7 遍 DOM"。写探针实测后**这个判断站不住**，撤回：

| 方案 | 耗时（15KB markdown / 1642 个元素） | 相对现状 |
| --- | --- | --- |
| 现状：5 次独立原生扫描 | 1.97 ms | 1.00× |
| 单次 `querySelectorAll("*")` + JS 分派 | 3.8–4.7 ms | **1.8–1.9×（更慢）** |
| 单次 `TreeWalker` + 按 `nodeName` 分派 | 0.73 ms | 0.31× |
| 对照：`render(md)` 整条管线 | **216 ms** | — |

两个结论：

1. **`querySelectorAll("*")` 方案是负优化**——把 1642 个元素物化成数组再在 JS 里筛，
   比让原生选择器引擎按标签名走索引更贵。"合并成一次遍历"的直觉不成立。
2. **即便用最优的 `TreeWalker`，也只省下 0.58% 的渲染时间**（1.97ms → 0.73ms，对 216ms 的管线），
   而且渲染结果按 `content` 缓存，这 0.58% 只在真正重新渲染时才付一次。

为此去改 5 个承载"导出还原契约"（`data-vs-video-src`、`vs-*-placeholder` 等）的 effect，
风险远大于收益。**结论：不做。**

> 注：MathJax / Mermaid 那两个 effect 本来就有 `html.includes(...)` 短路，没命中时压根不扫。
> jsdom 的选择器引擎是 JS 实现，绝对值比真实 WebView 慢一个量级，有意义的是相对关系。

### 2.2 顺带修掉：测试产物污染源码树

查 §2-D 时发现 `src/components/` 下有 **19 个孤儿文件**（`DocTree/` 14 个、`Publish/` 5 个，
最早可追溯到 9 月 13 日），都是 `*.runtime-<pid>.mjs`。

根因：三个测试（Preview / DocTree / Publish）都要先用 esbuild 打一个运行时包再 `import`
（因为 `src/store` 链路用了 Vite 的 `import.meta.glob`，node:test 直接加载会失败），
而它们把产物**写在了源码树自己的目录下**，只靠 `.gitignore` 遮住 + `after()` 钩子删掉。
一旦清理失败（例如被沙箱的批量删除守卫拦下 `unlink`），产物就永久留下。

**位置其实被两个约束卡死**：

1. 不能放系统临时目录 —— 这些包配了 `packages: "external"`，react / react-dom 等裸包名
   会**保留为运行时 import**，由 Node 从产物所在目录向上找 `node_modules`。
   实测放 `os.tmpdir()` 会直接 `ERR_MODULE_NOT_FOUND: Cannot find package 'react'`。
2. 也不该放源码树 —— 见上。

折中：新增 `src/test/tempRuntime.ts`，统一写到**仓库根的 `.vs-test-runtime/`**。
既在 `node_modules` 解析范围内，又不在 `src/` 里，tsc / vite 都扫不到；
`.gitignore` 补一条 `.vs-test-runtime/`。

> 教训：**先改位置再改清理策略**。这次我先按"写到系统临时目录"改，被
> `ERR_MODULE_NOT_FOUND` 打回 —— 55/67 个用例直接挂掉。原因就是没先确认
> esbuild 的 `packages: "external"` 会把这些包留成运行时 import。

### 2.3 为什么也放弃了「867KB chunk 分片」（实测）

我原本写的是"这一个 chunk 仍然很重，改为按分页分片懒加载，滚到哪加载哪"。实测数据：

| 指标 | 实测值 |
| --- | --- |
| 原始大小 | 887,456 bytes |
| **gzip 后** | **78,947 bytes** |
| V8 解析 + 执行 | **~12 ms**（同一进程内多次 `import` 稳定在 12–13ms） |
| 加载时机 | 只在**首次**打开代码主题选择器时，之后走 module cache |

**12ms、78KB、只加载一次** —— 这不是"重"，是正常的按需加载。

更关键的是分片会连带破坏三处现有行为：

1. **跨全部主题搜索**：`filterAndRankCodeThemes(CODE_THEMES, query, …)` 是在整个数组上
   按 `name` / `id` / `group` 过滤的（`themePickerModel.ts:39-48`），分片后搜不全；
2. **计数显示**：`ThemePickerDialog.tsx:448` 直接渲染 `{CODE_THEMES.length} 个主题`；
3. **同步取 CSS**：`CodeThemeThumbnail.tsx:25` 和 `Preview` / 导出链路都**同步**调用
   `buildCodeThemeCss`，改成按需加载就得把这条链变异步 —— 而它同时服务预览与导出成品，
   是正确性关键路径。

**结论：不做。** 为一个 12ms 的按需加载去动正确性关键路径，是明显的负收益。

> 这一条和 2.1、§2 表 D 一起说明一件事：原始评估里"前端可优化项"有相当一部分是
> **看着像问题、实测不是问题**。真正站得住的只有 §1 的字号根因、§2 表 C 的缓存字节上限、
> 表 F 的重复注入，以及 §3 的 wximg 三项。

> 现在 `release.yml` 的 `timeout-minutes: 60` 还够用，但后续再往构建里加东西时要复核这个数。

> ⚠️ `panic = "abort"` 还能再瘦一圈，取舍见 3.2 —— **不要再把它当成"等 unwrap 清理完"的待办**，
> 那个前置条件本来就不存在。

**顺带发现（未实施）**：`tauri.conf.json` 的 `build` 段可加 `"removeUnusedCommands": true`，
让构建期把 ACL 里没授权的 IPC command 从 `generate_handler` 中摘掉。本机 `tauri 2.11.2` /

### 3.1 wximg 取图路径的三个问题（已修）

这一节是查 D 项时顺带挖出来的，**A 项是真实 bug**。

**① `fetch_proxied_image` 没写 `.no_proxy()` —— 代理用户会看不到预览图。**

`reqwest` 的 `ClientBuilder` 默认 `auto_sys_proxy = true`（`reqwest-0.12.28/src/async_impl/client.rs:309`），
`build()` 时会 `push(ProxyMatcher::system())`，读 `HTTPS_PROXY` / `HTTP_PROXY` / `ALL_PROXY`
以及系统代理设置；只有 `.no_proxy()` 会把它关掉（同文件 `:1416`）。

本仓库其它取图/取 IP 路径都显式写了 `.no_proxy()`：`wechat/token.rs`（`get_outbound_ip`）、
`wechat/upload.rs`、`preview_image/http.rs`（`direct_http_client_builder`，还有专门的测试
`preview_http_clients_explicitly_bypass_system_proxies` 强制要求）。**只有 wximg 这条漏了。**

后果：用户机器上代理常"配着但没启动"（Clash / v2ray 退出后环境变量还在），
于是预览里所有 mmbiz 图都会连不上代理而加载失败。**本次机器上就复现了**
（`HTTPS_PROXY=http://127.0.0.1:11233` 是设着的）。

已补 `.no_proxy()`，并加了源码扫描测试 `proxied_image_client_is_shared_and_bypasses_system_proxies` 防回归。

**② 每张图都新建一个 `reqwest::Client`。**

原来 `fetch_proxied_image` 内部每次调用都 `Client::builder()...build()`，
等于每张图重新建连接池、重新 TLS 握手（一篇文章 40 张图 = 40 次握手）。
已抽成 `proxied_image_client()`，进程内 `OnceLock` 共用一条连接池。

**③ 没有磁盘缓存。**

响应虽然带 `Cache-Control: max-age=86400`，但**自定义协议的响应不会落进 WebView 的磁盘缓存**，
重启应用后整篇文章的图都要重新拉。已新增 `src-tauri/src/wximg_cache.rs`：

- 落盘 `app_data_dir/cache/wximg/`，用户可以直接删目录清缓存；
- 文件名 = URL 的 FNV-1a 哈希（与 `history.rs` 同一套固定算法，工具链升级后仍能命中旧文件）；
- 文件自带头部（magic + content_type + 原始 URL），读取时**校验 URL 一致**，
  哈希碰撞时判为未命中，避免把 A 图当 B 图返回；
- 256MB 总量上限 + 单张 8MB 上限，写入后按 mtime 淘汰最旧；
- 临时文件 + rename 落盘，避免半截文件被当成有效缓存；
- **纯加速层**：任何一步失败都静默退化成"没有缓存"，绝不影响取图本身。

顺带把响应构造里的 `unwrap()` 换成了过滤控制字符 + 兜底空体，避免上游返回畸形
`Content-Type` 时一次取图把进程带走。

### 3.2 更正：`unwrap()` 统计错了，生产代码几乎没有 panic 面

原文 §3 表 B 说"`preview_image.rs` 112 处 `unwrap()/expect()`、`wechat.rs` 34 处"，
并建议"高频路径换成 `map_err`"。**这个统计是错的** —— 我数的是整个文件，没有排除测试模块。

按 `#[cfg(test)] mod tests` 分界重新统计：

| 文件 | 总数 | 生产代码 | 说明 |
| --- | --- | --- | --- |
| `preview_image.rs` | 112 | **0** | 112 处全在测试模块内（测试里 panic 正是期望行为） |
| `wechat/`（原 `wechat.rs`） | 38 | **4** | 4 处都是 `TOKEN_CACHE.lock().unwrap()` |
| `wechat_backend.rs` | 4 | **0** | 全在测试模块内 |

生产代码的全部 panic 面：

- 4 处 `Mutex::lock().unwrap()`（拆分后为 `wechat/token.rs:31/55/86/91`）—— 只有锁被 poison
  （即有线程持锁时 panic 过）才会 panic，是 Rust 惯用写法；
- 2 处 `unreachable!()`（`preview_image/asset.rs:186`、`preview_image/commands.rs:88`）—— 都在
  `if kind == ImageKind::Svg { … return }` 之后，只为 `match` 的穷尽性存在，**证明不可达**。

**结论：`panic = "abort"` 的前置条件本来就基本满足，不需要那轮"unwrap 清理"。**
是否开启只剩一个取舍：`abort` 取消 unwind，panic 直接结束进程（干净崩溃 + 重启），
而不是留下一个静默损坏的中间状态。这个取舍应当单独决定，不要和"清理 unwrap"捆在一起。

### 7.1 两个必须知道的技术点

1. **重导出必须用 glob，不能逐个列名字。** `#[tauri::command]` 除了包装函数，还会在
   **命令所在模块**里生成 `pub use {__cmd__X, __tauri_command_name_X};`
   （`tauri-macros/src/command/wrapper.rs:351`），而 `lib.rs` 的 `generate_handler!`
   是按 `wechat_backend::X` 去**该路径**找这两个宏的（`command/handler.rs:161`）。
   逐个列名字只重导出函数、漏掉宏 → 28 个命令全部报 E0433。
   用 `pub(crate) use <子模块>::*;` 才能把宏一起带出来，从而**不必改 `lib.rs`**。

2. **子模块用 `use super::*;` 继承公共导入。** 这样 `use tauri::{...}` 和
   `#[cfg(windows)] use webview2_com::...` 只写一份，各子模块共享。
   代价：跨子模块的私有项要放宽到 `pub(crate)`（原文件里的
   `#[cfg_attr(not(windows), allow(dead_code))]` 注解全部保留，非 Windows 的
   dead_code 行为不变）。

### 7.2 踩到的坑：区间重叠把函数抄进了两个文件

拆的时候我按"行号区间"搬运，`content` 取了 `(639, 1118)`，`window` 又取了 `(654, 732)`
—— 后者**完全落在前者里面**，于是 `eval_in_backend_window` 被同时写进了
`window.rs` 和 `content.rs`。

**这个错误能编过。** Rust 允许不同模块有同名函数，`cargo check` 只会因为两个
glob 都带出这个名字而报一个 **E0659 歧义**。当时我把它误判成"glob 循环引用"，
加了一行显式 `use window::eval_in_backend_window;` 压住就过去了 —— 但那只是把
症状盖住，两个副本还在。

真正的暴露来自**逐模块核对闭合花括号数量**：`content.rs` 比原区间多 7 个 `}`。
修法是让区间不重叠（`content` 改成 `(15,52) + (639,652) + (733,1118)`），
并在拆分脚本里加一条区间重叠断言。

> 教训：机械搬运代码时，"能编译 + 测试通过"**不足以**证明搬对了 ——
> 区间重叠造成的重复定义恰恰是编译期合法的。必须另外做一次
> **逐模块的结构计数核对**（这里用闭合花括号数）才能兜住。

### 8.3 两个会浪费时间的环境坑（这次踩到了）

### 9.1 这次的新坑：`impl` 块里的方法也要放宽

`wechat.rs` 拆分时已经踩过"结构体字段要放宽"（E0616）。这次又发现一个新类别：
**`impl` 块里的私有方法被别的模块调用会报 E0624 "method is private"**。

`asset.rs` 的 `impl ImageKind { fn mime_type(self) ... fn extension(self) ... }` 被
`commands.rs` 调用（`kind.mime_type()` / `kind.extension()`）。`widen()` 的顶
层正则只匹配行首无缩进的 `fn`，`impl` 块里的方法 indented 了，所以漏掉。

修复：在 `widen()` 里追加 `widen_impl_methods()` —— 遇到 `impl ... {` 后进入状态机，
用 brace depth 追踪，只在 **depth == 1**（即 `impl` 体内的第一层）时把 `fn ` 改成
`pub(crate) fn `。`depth == 1` 是为了不宽放过深的嵌套函数（Rust 不允许 impl 里直接
嵌套函数，但 match/arm 里可能有闭包或嵌套块，误改它们没意义）。
